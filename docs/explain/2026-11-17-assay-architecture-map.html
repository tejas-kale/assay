Assay's architecture, part 1: the map

6 min read · 2026-11-17
Answer

Assay is two programs that never call each other directly. One is the app: the window, the panes and the Trust buttons. The other is Claude's side: Claude Code, plus Assay's plugin, the assay server and the Python kernel. They communicate only by writing and reading files in the analysis folder.

Moving to the Claude desktop app replaces how Claude's side is started and contained. The files in the middle and the app's role as the only one who can trust a calculation can stay as they are.

The map

Everything you see in Assay belongs to one of two sides. The left half of the window, the terminal, is Claude's side. The right-hand panes (Data, Plots, Steps, Trust and the rest) belong to the app. The two sides share one thing: the analysis folder on disk.

One run, start to finish

Here is what happens when you ask Claude for a number and it appears in the Data tab. Each step names the file where it happens, so you can open the code if you want to.

0. The app starts Claude src/core/session.ts:34-60

When you open an analysis, the app opens a terminal and starts claude in it, through your login shell so that it finds the same programs a normal Terminal would. It gives Claude two things: Assay's plugin (--plugin-dir) and the assay server (--mcp-config). It also sets variables such as ASSAY_ANALYSIS (which folder is open) and ASSAY_VENV (which Python to use).

If you set ASSAY_CLAUDE_BIN, the app starts that program instead of claude. Your Podman wrapper uses this to run Claude inside a container. The full rules for a launcher are in docs/developer/launch-contract.md.

1. You type; a hook adds the rules src/hooks/prompt.ts, src/core/rules.ts

Before Claude sees your message, the plugin's prompt hook adds Assay's rules to it: which analysis is open, that Python goes through the python tool, which trusted calculations exist, and which runs you made yourself since your last message. This happens on every message you type.

2. Claude calls a tool, and hooks check it src/hooks/bash.ts, write.ts

Claude decides to run SQL and calls mcp__assay__sql. Other hooks check other tools: one stops Python from being run through Bash, and another stops Claude from writing into trusted/, dictionaries/, queries/ or another analysis. A hook can refuse a tool call before it runs. That makes hooks the strongest rules Assay has inside Claude Code.

3. The server checks the SQL, numbers it and runs it src/server/sqlRun.ts

The assay server is a small Node program that Claude Code starts at the beginning of the session and stops at the end. It first applies Assay's SQL rules and expands any trusted blocks you include, then saves the statement under the next free number (say queries/042.sql) and runs it on Databricks or Postgres. Python goes the same way, except that it runs in the kernel (src/server/pythonRun.ts).

4. The kernel keeps your variables src/server/kernel.ts, python/analysis_kernel.py

The kernel is one long-running Python process per session, like a Jupyter kernel. Claude's Python runs and your re-runs from the app all go to this same kernel, so a variable that Claude creates is there when you re-run something. This is the "one place where code runs" in Assay's first rule.

5. The app notices the new run and shows it src/main/windowWatch.ts:29-31

The app checks the analysis folder for changes to queries/, .assay/runs.json, the threads and the trust files. When 042 appears, the Data and History tabs redraw. The app never asked the server for anything: it only saw a new file.

6. You re-run from the app: the same path, backwards src/server/requests.ts

When you press Cmd+Enter on a run, the app writes a request file, .assay/requests/<id>.json. The server checks that folder every 500 ms, runs the code in the same kernel, saves it as a new numbered run marked as yours, and writes the answer to .assay/replies/. On your next message, the prompt hook tells Claude what you ran.

Why files sit in the middle

The README says "the files are the contract between the two, and the app keeps no database". This one choice explains most of the design:

  • Claude's side can run somewhere else. The Podman wrapper runs Claude in a container that sees the same folder at the same path. The app doesn't need to know, because it only reads files.
  • Every run is a file you can open. queries/042.sql and its results are on disk, numbered and never changed afterwards. That's what makes the record of an analysis trustworthy.
  • Neither side can make the other do anything. A request file asks the server to run code. It can't make anything trusted, because only the app's Trust buttons do that (next section).

The cost: anything on Claude's side that can write files can also write a fake request. A forged request file can make a run look like yours. The security doc lists this as a known gap (PI-1, docs/developer/security.md, "Known gaps").

Who may write what

Who may write which file is the core of Assay's safety. One rule matters more than the others: nothing becomes trusted unless you press Trust in the app.

WhatWho writes itWhat stops anyone else
Runs in queries/The server onlyThe write hook refuses Claude's Write and Edit there
A run's "made by you" markThe server onlyThe server removes header lines that Claude's code tries to add
trusted/, dictionaries/The server, after you approveThe write hook, and the server copies only what the ledger allows
Trust ledgerThe app onlyIt sits in the app's data folder; a launcher must mount it read-only
Requests in .assay/requests/The appThe write hook (Claude's code can still write one: PI-1)
Your notes, drafts in lib/You and ClaudeClaude uses note and revise_note, not Write

These rules come in two strengths. Hooks stop a Claude that follows the rules. They can't stop code that's already running: the kernel runs any Python Claude writes, as you, with your permissions. Containing that code is left to the launcher (your Podman wrapper). With plain claude and no container, a Claude that was tricked by text in the data could do anything your Mac account can do (docs/developer/security.md, "The isolation boundary").

Words you will meet

These words come up in every later page.

TermPlain meaningUsed in a sentence
PluginA bundle that adds tools, rules and commands to Claude Code"The plugin's hooks stop Python going through Bash."
HookA small script Claude Code runs at a fixed moment, such as before a tool call; it can refuse the call"The write hook refuses edits to queries/."
SkillA written procedure Claude loads when a task matches it"assay:wrap-up closes threads and writes root notes."
MCP serverA separate program that gives Claude new tools; Claude Code starts it and talks to it"sql and python are tools of the assay MCP server."
KernelA long-running Python process that keeps variables between runs"Your re-run used the frame Claude made, because it's the same kernel."
LauncherThe program the app starts instead of plain claude, usually to contain it"The Podman wrapper is a launcher."
Trust ledgerA file listing the fingerprints (sha256 hashes) of the calculations you approved"A trusted file that was edited no longer matches the ledger, so it isn't trusted."
SandboxA limit set by the operating system on which files and network hosts a program can reach"In Claude Code, the sandbox covers Bash commands, not MCP servers."

The two rules worth keeping through the move are "one place where code runs, every run recorded" and "only your click in the app trusts anything". Both live in the middle and left of the map, and the desktop move mostly changes the right.
